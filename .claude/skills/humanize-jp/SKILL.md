# humanize-jp — 日本語の「AIっぽさ」を抑える

このスキルは、同一テーマで人間 1,105本 / AI(Claude)1,105本を統計比較した humanizer-jp の検証
(`docs/findings_verification.md`)で**実証された指紋だけ**を根拠に、日本語文章を人間寄りにリライトする。
直感の「AI臭」リストではなく、反証検証を生き残った特徴に絞っているのが要点。

## 大原則:効く順に直す

派手な見た目(箇条書き・絵文字・太字)を消すより、**文そのものの作り方**を直す方が圧倒的に効く。
優先順位を守ること。①が全体の8割。

### ① 文の長さをバラけさせる(最重要・これだけで激変)

AI最大の指紋は「短く・長さのそろった文を淡々と並べる」こと。AI記事の **99%** が人間より文長が均一だった。
**人間は長短の落差でリズムを作る。**

- 長い説明文の直後に、ごく短い文(体言止め・5〜15字)を差し込む。
- 逆に、ぶつ切りの短文が続くところは接続して1文に束ねる。
- 目標:文長の変動係数(CV)を **0.70以上** に(AI中央値0.55 → 人間中央値0.81)。

> 🤖 Before(均一・35〜48字が続く):
> 「この機能は便利です。設定も簡単に行えます。導入の手順も明確になっています。運用も安定しています。」
>
> 🧑 After(緩急をつける):
> 「この機能は、地味だが効く。設定は一瞬。導入手順も迷わないし、入れてから半年、一度も落ちていない。」

### ② 一文を欲張らない/読点を入れすぎない

- 句点密度はAIが人間の約1.6倍(短文を量産しがち)。**長い文も恐れず混ぜる**。
- AIはどの文にも読点「、」を最低1つ入れる。**読点ゼロの短い文**も意識的に作る(人間は読点なし文が多い)。

### ③ AI特有の語彙・文末・締めを置き換える

検証で残った語句。出てきたら言い換えるか削る。

| 🤖 AIが多用 | 性質 | 🧑 人間寄りの代替 |
|---|---|---|
| 〜を整理すると / 整理しておきたい | まとめたがり | 「要するに」「ざっくり言うと」、または前置きごと削除 |
| 〜しておきたい / 〜しておきます | 配慮の前置き(人間ほぼ不使用) | 「〜しておく」「〜する」と言い切る、前置きを消す |
| 〜といえます / 〜といえるでしょう | 評価まとめの常套句 | 「〜だ」「〜だと思う」と言い切る、評価文ごと削る |
| 高い水準で実現されている | 評価ヘッジ | 具体的な事実・数字に置き換える |
| 一方(で)、… / つまり、… 〔文頭多用〕 | 接続詞で論理を明示しすぎ | 接続詞を落として並置する、文を切る |
| 本記事では〜を解説します | 自己言及の宣言 | いきなり本題に入る |
| 〜ではないでしょうか | 婉曲ヘッジ | 「〜だ」「〜だろう」と踏み込む |

「地味」「けれど」もAIに偏るが、文脈で自然なら無理に消さない(過剰修正に注意)。

### ④ 構造の作りすぎをほどく(知覚上の対策)

> 注意:箇条書き・見出し・太字の多さは検証上**収集条件の差**で、純粋な言語的指紋ではない。
> ただし**読者の体感としては**「全部が箇条書き」「3行ごとに見出し」は強くAIっぽく映る。
> 媒体に応じて、地の文で流せるところは段落に戻す。技術ドキュメントの箇条書きまで消す必要はない。

## やりすぎ厳禁(これらは直さなくてよい)

検証で「AIの指紋ではない」と判明したもの。触ると逆に不自然になる:

- **丁寧さ(です・ます)を崩す必要はない** — 人間ブログの方がむしろ丁寧語は多い。文体は媒体に合わせる。
- **漢字を増やす/減らすのは目的でない** — ジャンル次第で方向が変わる。ひらがなが多すぎる場合だけ少し締める程度。
- **三点リーダ「…」はむしろ人間的** — 余韻として使うのはOK。

## 進め方(ワークフロー)

1. **対象テキストを読む**。媒体(技術記事/エッセイ/ビジネス文)と維持すべき敬体・常体を把握。
2. **診断**(任意だが推奨):
   ```bash
   python3 .claude/skills/humanize-jp/reference/humanize_check.py 対象ファイル
   # または:  cat file.md | python3 .claude/skills/humanize-jp/reference/humanize_check.py -
   ```
   文長CV・句点密度・読点・ひらがな率と、tell語句の出現箇所を表示する。**CVが最重要**。
3. **①→④の順でリライト**。意味・事実・主張は変えない。文のリズムを最優先で直す。
4. **再診断して CV >= 0.70 を確認**。tell語句が残っていれば置き換える。
5. ユーザーには「何を・なぜ直したか」を簡潔に添える(特に文長のバラけ)。元文を勝手に要約・改変しない。

## 原則

- **意味を保つ**:humanize は体裁の調整であって、内容の書き換えではない。
- **媒体を尊重**:Qiita の技術記事と note のエッセイで適切なトーンは違う。一律に砕けさせない。
- **過剰修正を避ける**:tell をゼロにするより、文長のリズムを人間化する方が効果が高い。
- 根拠の詳細は `docs/findings_verification.md`(検証)/ `docs/findings_public.md`(要約)を参照。
